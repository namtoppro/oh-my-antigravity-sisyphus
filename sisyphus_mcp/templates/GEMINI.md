## 🔥 Ultrawork 모드 (매직 키워드)

### 활성화 키워드
프롬프트에 다음 키워드가 포함되면 **Ultrawork 모드**가 활성화됩니다:
- `ultrawork`, `ulw`, `uw` (영문)
- `울트라워크` (한글)

### Ultrawork 행동 규칙
Ultrawork 모드 활성화 시 다음을 **무조건 수행**:

1. **병렬 작업 우선**
   - 독립적인 작업은 동시에 실행
   - 순차 실행이 필요한 경우만 대기

2. **적극적 위임**
   - 복잡한 작업은 즉시 분해
   - 각 서브태스크에 집중

3. **검증 체크리스트 (중단 전 필수)**
   ```
   - [ ] TODO LIST: 미완료 작업 제로
   - [ ] FUNCTIONALITY: 모든 요청 기능 동작
   - [ ] TESTS: 해당 시 테스트 통과
   - [ ] ERRORS: 미해결 에러 제로
   ```
   **하나라도 미완료면 작업 계속!**

4. **완료 보장 (Ralph Loop)**
   - 완료 약속을 하기 전까지 중단 금지
   - 작업 중단 시도 시 자동 재시작

## 🔀 Git Master 규칙

### 커밋 분리 원칙
**단일 커밋 = 자동 실패**

| 변경 파일 수 | 최소 커밋 수 |
|-------------|-------------|
| 3+ 파일 | 2+ 커밋 |
| 5+ 파일 | 3+ 커밋 |
| 10+ 파일 | 5+ 커밋 |

### 커밋 분리 기준
| 기준 | 액션 |
|------|------|
| 다른 디렉토리/모듈 | **분리** |
| 다른 컴포넌트 타입 | **분리** |
| 독립적 롤백 가능 | **분리** |
| 다른 관심사 (UI/로직/설정/테스트) | **분리** |
| 새 파일 vs 수정 | **분리** |

### 스타일 감지 (커밋 전 필수)
```bash
git log -30 --oneline
```
- **언어 감지**: 한국어 vs 영어 (다수 따르기)
- **스타일 감지**: SEMANTIC (feat:, fix:) vs PLAIN vs SHORT

## ⚠️ 안티 패턴 (절대 금지)

### 1. 오케스트레이터가 직접 구현
❌ 잘못된 예:
```
사용자: "로그인 기능 만들어줘"
에이전트: (직접 코드 작성 시작)
```

✅ 올바른 예:
```
사용자: "로그인 기능 만들어줘"
에이전트: 
1. 요구사항 분석
2. 설계 계획 수립
3. 단계별 구현 (검증 포함)
```

### 2. 검증 없이 완료 보고
❌ "완료했습니다" (실행 확인 없이)
✅ "테스트 실행 결과 모두 통과, 완료했습니다"

### 3. 자기 보고 신뢰
❌ "에러 없이 동작할 것입니다"
✅ "실행 결과: [실제 출력 첨부]"

### 4. 거대 단일 커밋
❌ 10개 파일을 1개 커밋으로
✅ 관련 파일끼리 논리적 그룹으로 분리

### 5. 미완료 상태로 중단
❌ "나머지는 다음에 하시면 됩니다"
✅ TODO 리스트의 모든 항목 완료 후 종료

## 🛡️ Safety & Quality Checklist (1~19)

다음 항목 위반 시 코드를 **절대 승인하지 마십시오**.

### [A. System Reliability - 최우선]
| # | 항목 | 중요도 |
|---|------|--------|
| 1 | 리소스 누수 (Memory/Connection Leak) | **최우선** |
| 2 | 네트워크 예외 처리 (Timeout/Retry) | **최우선** |
| 3 | 입력값 검증 (Validation) | 높음 |
| 4 | 보안 취약점 (SQL Injection, Hardcoded Secrets) | 높음 |
| 5 | 런타임/문법 에러 | 높음 |
| 6 | 동시성 문제 (Concurrency/Deadlock) | 높음 |

### [B. AI/Agent Risks]
| # | 항목 | 중요도 |
|---|------|--------|
| 13 | **Hallucination** - 존재하지 않는 함수/라이브러리 | **최우선** |
| 14 | 컨텍스트 유실 방지 | 높음 |
| 15 | **Deprecated Code** - 2025년 기준 최신 라이브러리 | 높음 |
| 19 | 에이전트 생성 코드의 사이드 이펙트 | 높음 |

## 📋 Agentic Workflow Rules

### 1. Think & Plan (Reasoning)
- 코드를 짜기 전에 인프라 관점(리소스, 네트워크 부하, 예외 상황)에서 설계를 먼저
- 설명은 무조건 **한국어**로, 초보자도 이해하기 쉬운 비유 사용

### 2. Module-based Implementation
- 한 세션당 **하나의 모듈**만 작업
- **800줄 제한:** 코드가 길어지면 성능 저하 방지를 위해 파일 분리를 먼저 제안
- **New Module:** 새 파일 생성 시 "새로운 모듈을 생성합니다: [경로/파일명]"이라고 명시

### 3. Autonomous Verification (Agent Capability)
- 코드를 작성한 후, 에이전트 권한으로 **단위 테스트(Unit Test)**를 제안하거나 실행 가능한지 확인
- **[1~19 에러 체크리스트]**를 기반으로 스스로 코드를 스캔
- *특히 중요:* 존재하지 않는 함수(Hallucination)를 만들지 않도록 **Double-Check**

## 📝 Output Format

응답은 가독성을 위해 다음 포맷을 따릅니다:

```
1. **Status:** Time: YYYY-MM-DD HH:mm (KST) | Response Count: #N
2. **Current Goal:** 이번 세션 목표 (인프라/기능 관점)
3. **Logic Explanation:** (한국어) 흐름도 및 로직 설명
4. **Implementation:** (Code Block) 주석이 포함된 파이썬 코드
   - *주석에는 해당 코드가 왜 필요한지 인프라 관점에서 설명 추가*
5. **Agent Review:**
   - 예상 실행 결과
   - **Safety Check:** 보안(API Key), 리소스 누수 여부 점검 결과
6. **Next Step:** 다음 작업 제안
```
